# Experimental methodology

How every number in this directory was produced, and how to reproduce it.

## 1. Design of the comparison

The baseline and the fault-tolerant system are **the same container image**. They
differ only in two environment variables:

| Variable | Baseline | Fault-tolerant |
|---|---|---|
| `FT_ENABLED` | `0` | `1` |
| `RESTART_POLICY` | `no` | `unless-stopped` |

`FT_ENABLED` is read at the point of use, not at import, and gates every software
mechanism: retry, per-attempt timeout, circuit breaker, health polling, replica
read failover, idempotency-key handling, the recovery sweep and stale-cache
degradation. `RESTART_POLICY` gates the infrastructure-level self-healing.

Because nothing else differs -- same code, same image, same database, same host,
same workload, same injection at the same offset -- any measured difference is
attributable to those mechanisms. Every log line carries `"ft": 0|1`, and the
deployed mode is written to `.env` and reported by `GET /health`, so a run cannot
be silently misattributed to the wrong version.

## 2. Workload

Generated by `scripts/workload.ts` against the gateway on port 8080.

* **Concurrency:** 10 workers, each issuing one request at a time with a 50 ms
  think time between requests. The high-load scenario adds 100 more workers at
  T+20 s.
* **Mix:** 60 % `GET /api/students/{id}`, 20 % `GET /api/transcripts/{id}`,
  20 % `POST /api/payments` for a fixed amount of 100.
* **Student selection:** uniform over the 200 seeded students.
* **Payment intents:** every payment carries a unique `Idempotency-Key`. With
  probability 0.2 the same intent is sent a second time, modelling the client who
  did not see a response and retried. A correct system charges such an intent
  exactly once; this is what the duplicate-charge count measures.
* **Client timeout:** 10 s, representing the patience of a real user. A request
  that exceeds it is recorded as failed with `err: "client_timeout"`.
* **Window enforcement:** the generator aborts every in-flight request when the
  window closes, so a hung request cannot extend the observation period. Requests
  aborted this way are recorded as `abandoned_at_window_close` and counted as
  failures, because they had not completed within the window.

## 3. Timing of a run

Every run follows the same schedule, driven by `scripts/run.ts`:

| Offset | Event |
|---|---|
| before T+0 | platform restored (`docker compose start`), all five instances polled until healthy, streaming replication confirmed, `payments` truncated and balances reset |
| T+0 | workload starts |
| T+20 s | fault injected |
| T+45 s | operator repair issued |
| T+70 s | workload stops, window closes |

The repair is issued in **both** versions. In the fault-tolerant version the
system has usually healed itself long before and the command is a no-op; issuing
it anyway means the baseline's MTTR reflects a plausible human response (25 s)
rather than infinity, which keeps the comparison meaningful.

Resetting the ledger before each run means duplicate-charge and orphan counts
belong to that run alone.

## 4. What is recorded

Two raw files per run, both in the run's directory:

* `workload.jsonl` -- one line per client request: timestamp, operation, HTTP
  status, success, degraded flag, duration, error, payment intent, whether it was
  a client resend.
* `events.jsonl` -- one line per service-side event in the window, sliced out of
  the shared `logs/events.jsonl` by byte offset (the services hold the file open,
  so it cannot be rotated). Event kinds: `request`, `attempt`, `upstream`,
  `route`, `health`, `breaker`, `recovery`, `degraded`, `chaos`, `db`.

`metrics.json` holds everything computed from those two files, and `REPORT.md`
renders it with the timeline and the consistency verdicts.

## 5. Metric definitions

Defined once, at the top of `scripts/metrics.ts`, and applied identically to both
versions:

* **bin** -- one second of wall clock. UP if at least one request in it succeeded,
  DOWN if it contained requests and none succeeded, IDLE if it contained none.
  IDLE bins are excluded from availability rather than assumed up.
* **outage** -- a maximal run of consecutive DOWN bins; its start is the first
  failed request and its end the first success that follows.
* **MTTR** -- mean outage duration.
* **MTTF** -- mean length of the operating intervals preceding an outage. With no
  outage in the window the value is right-censored and only a lower bound is
  stated: `MTTF > observation window`. This is reported honestly rather than as
  "infinite" or "0".
* **MTBF** -- mean time between successive outage onsets; with fewer than two
  outages it is reported as MTTF + MTTR, and the source is labelled.
* **Availability** -- reported two ways, because they answer different questions.
  *Time-based* (UP / (UP + DOWN)) answers "was the service up?". *Request-based*
  (successful / total) answers "did my call work?". A system that hangs rather
  than fails scores well on the second and badly on the first; a system that fails
  fast does the opposite. Both are needed.
* **Detection time** -- from injection to the first evidence the system had of the
  fault, from any source: a failed call attempt, a failed health probe, or a
  client-visible failure. A well-behaved system detects long before any client is
  affected, which is why a failed *attempt* counts.
* **Recovery time** -- from injection to the end of the outage it caused. Where a
  fault never reached a client there is no outage and the report says so rather
  than printing a misleading zero.
* **Absorption time** -- from injection to the last internal failure. Meaningful
  even when the fault was fully masked, because it says how long the mechanisms
  were actively compensating.

## 6. Data-consistency checks

After the window closes, `scripts/run.ts` queries the database directly, and the
per-intent verdict is computed from the client's own observations.

**Duplicate charges** are counted per intent, never by subtracting aggregates.
The discriminator is the HTTP status the client received: `201` means a new charge
was created for that request, `200` means the request was recognised as a
duplicate and nothing was charged. A second `201` for the same intent is therefore
by definition a second charge. The baseline never returns `200`, because it
ignores the idempotency key entirely.

**Unacknowledged intents** are intents for which the client never saw a charge
confirmed. Some of them may have been charged server-side with the response lost,
so this is an upper bound on lost transactions rather than an exact count. It is
reported separately from duplicates because the two are opposite failures: one
takes money twice, the other takes none and is safe to retry.

**Orphaned checkpoints** are payments still in `pending` in the database. Each one
is money neither charged nor released, with no process that will reconcile it.

**Ledger balance** compares the sum of completed payment amounts against the sum
of student balances; the two must agree.

## 7. Reproducing the campaign

```
npm test                 # self-check of the fault-tolerance core
npm run up:ft            # deploy the fault-tolerant version
npm run campaign         # all six scenarios
npm run up:baseline      # deploy the baseline
npm run campaign         # the same six scenarios
node --experimental-strip-types scripts/compare.ts
```

A single scenario: `npm run exp <app-crash|db-failure|net-timeout|node-failure|txn-interrupt|high-load>`.

`EXPERIMENT-LOG.md` is regenerated from every run's `metrics.json` on each run, so
repeating a scenario replaces its row rather than adding a second one.

## 8. Campaign history

Two defects were found and corrected during the campaign. Both invalidated data
that had already been collected, and in both cases the affected runs were
repeated rather than reinterpreted.

**2026-09-21 -- unbounded observation window.** The first baseline campaign
produced three runs whose 70 s window had stretched to 357 s, 150 s and 262 s. The
cause was the baseline itself: with no timeout anywhere, a request hung on a stale
keep-alive connection to a restarted container, and the workload generator waited
for it. The generator now aborts in-flight requests when the window closes. The
three runs were repeated; the window length of every run is published in
`EXPERIMENT-LOG.md` so this class of distortion is visible rather than hidden.

**2026-09-22 -- health probe inherited the database's latency.** `GET /health`
queried the database with no deadline of its own. During the database-failure
experiment the probe took longer than the gateway's 500 ms probe timeout, so the
transcript service was marked unhealthy and removed from rotation even though it
could still serve its cache -- the graceful-degradation mechanism was being
defeated by the health check meant to protect it. The probe now has a 300 ms
budget, comfortably inside the prober's. Because this changes behaviour under
fault, **the entire twelve-run campaign was repeated** on the corrected code; the
earlier data is kept in `../results-before-healthfix/` for comparison and is not
reported.

**2026-09-22 -- duplicate-charge metric counted the wrong thing.** The first
definition was `completed payments in the database - distinct intents the client
saw succeed`. It produced false positives: a payment completed by the server whose
response the client never received looked like a duplicate. Redefining it as
`completed - distinct intents sent` fixed that but introduced the opposite error,
because duplicates and lost transactions cancel out in aggregate -- two baseline
runs with hundreds of real duplicates reported zero. The metric is now computed
per intent from the HTTP status the client received (a second `201` for one intent
is a second charge), which is exact and immune to both errors. No experiment was
repeated for this: the definition changed, the system's behaviour did not, so the
verdicts were recomputed from the stored raw data with `scripts/recompute.ts`.

The general rule applied here: when service code changes in a way that affects
behaviour under fault, the whole campaign is re-run. When only a metric definition
changes, the stored raw data is recomputed instead -- which is possible because
every run keeps its complete per-request and per-event logs.
